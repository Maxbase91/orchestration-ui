# Lessons

- React Query data used in a `useMemo` dependency must fall back to a module-level stable empty array. An inline `= []` changes identity on every render and can trigger a parent-update loop when the memo feeds `onUpdate`.
- A test script must declare its runner as a direct development dependency; never rely on a transitive executable surviving unrelated dependency cleanup.
- Varying a request payload does not invalidate a process-local serverless configuration cache. Integration tests that toggle cached admin state must poll through the documented TTL in both directions and include the final response status/body in a failure report.
- Dynamic intake conversations must be tested by matching the visible question to an answer, not by sending a positional answer array; question branching can otherwise put a value or critical-service answer into the wrong slot.
- UI walkthrough harnesses must treat valid funnel skips as success and propagate scenario failures through the process exit code; otherwise stale assumptions can hide broken coverage behind a green run.
- Neither `tsc -b` (this repo's app tsconfig uses bundler-mode module resolution) nor `vercel dev` (its dev-server loader is also lenient about missing extensions) catches a relative import in `api/*.ts` (or a module it imports) that is missing its file extension. Only Vercel's real per-function build — `npx vercel build`, then inspect `.vercel/output/functions/**/*.js` — enforces the strict node16/nodenext resolution the deployed Lambda actually runs under; a violation throws `ERR_MODULE_NOT_FOUND` at import time, before the handler body runs, producing a bare `500 FUNCTION_INVOCATION_FAILED` with no JSON body. Rule: any change to `api/*.ts` or a module it imports must run `npm run test:api-imports` (a static import-graph check, added for this), not just `tsc -b`; when in doubt, run `npx vercel build` and grep the emitted bundle directly rather than trusting `vercel dev`.
- A hook or mutation existing in the codebase and being correctly wired to Supabase does not mean it is wired to the UI — `useCreateFormSubmission()` was fully built and tested-pattern-correct but had zero callers anywhere, so every "Fill Out Form" submission silently discarded its input. Same root lesson as the chat-intake import bug, different mechanism: grep for actual callers before assuming a feature "works" just because its plumbing looks complete. Likewise a filter that reads as complete may be missing an obvious field — `forStage()` filtered by trigger stage but never checked template `status`, so `draft` forms were offered exactly like `active` ones.
- When a page accumulates tabs/sections over time, duplication creeps in unnoticed because each addition looks reasonable in isolation. Before adding new content to the request-detail page, check the ownership table in `docs/specs/design-document.md` §5.3 — the failure mode is a new section quietly repeating one that already exists elsewhere (this round found five real instances: header vs Documents tab, Compliance tab vs an embedded copy in Workflow, Documents tab vs a per-stage copy in Workflow, two separate comment systems in one stage card, and Related tab carrying content that belonged in Compliance).
- Presentation controls must remain semantically valid and usable at every breakpoint: interactive lifecycle stages should be real buttons containing phrasing content only, and a mobile drawer should force expanded labels even when the desktop sidebar was previously collapsed.
- When adding responsive variants to a flex layout, preserve the parent axis classes (`flex flex-col`) in the shared base class; otherwise desktop children can collapse into an unreadable strip even when their DOM remains present.
- Additive schema changes must be checked for duplicate `CREATE TABLE IF NOT EXISTS` blocks before merging; an earlier definition silently wins and can prevent later columns/constraints from ever being created.
- Every catalogue entry point must preserve the selected item identity through navigation. A route callback that stores a match in wizard state can still strand the requester at the catalogue structure; assert the CTA URL is `/catalogue/items/:id` in the browser smoke suite.
- A deployed data backfill cannot substitute for an unapplied schema migration: verify additive tables and columns in the target Supabase project before calling a governed flow production-ready. When an older prototype must remain usable, isolate a compatibility write and keep the migration requirement explicit.
- A provider migration must account for partially applied additive schemas: a missing optional table can produce a browser-level 404 even when the page renders. Gate reads behind an explicit capability flag and keep the migration tool able to skip absent legacy tables while reporting them.
- A row-count-complete database copy can still miss newly introduced governance links when the source schema predates the additive columns. Validate critical joins after migration and run an idempotent target-side backfill before calling the cutover ready.
- Never cache an expiring `AbortSignal` inside a module-level serverless database client; warm Vercel instances will reuse the aborted signal and turn later requests into immediate timeouts. Create the timeout per request/client.
- A live route sweep can expose a schema/code mismatch that static schema checks miss when a UI store names a relation separately from the main request model. Rule: inventory every relation used by browser stores and admin analytics, add it to the canonical schema and migration table list, and include it in the read-only Neon validation before declaring a deployment healthy.
- The Neon driver does not infer JSONB intent from JavaScript values: an array parameter can be stored as a PostgreSQL array-shaped object (`{}`). Rule: the database API must discover JSON/JSONB columns and serialize object/array write values explicitly before parameter binding.
- A route inventory must include links rendered only in role-specific home surfaces; a page can look healthy while its CTA points to a wildcard redirect. Rule: derive live route checks from both the router and each role's visible navigation/CTA URLs, then verify every link lands on its intended screen.
- Roadmaps become misleading when architecture and scope changes land faster than status prose. Rule: keep a separate evidence index for every Built capability, distinguish internal R1 writes from deferred upstream execution, and label simulation-only controls explicitly across the roadmap, README, ADRs, specifications, and test playbook.
- A governed checkout cannot retain a legacy direct-write fallback or rely on client-side numeric values. Rule: route every catalogue entry point through the atomic endpoint, and normalize Neon NUMERIC fields to numbers before policy evaluation so a string price cannot be rejected as invalid.
- A cart handoff must not silently drop additional lines when the destination currently accepts one line. Rule: block the handoff with an explicit message until multi-line item-detail checkout is wired, rather than navigating with only the first item.
- `npm run test:api-imports` inspects only **relative** specifiers, so a `@/`-aliased import inside a module reachable from `api/*.ts` is invisible to it. `tsconfig.api.json` maps `@/*` for tsc and Vercel's runtime does not, so a value import through that alias compiles, passes the guard, and throws ERR_MODULE_NOT_FOUND in the deployed Lambda. Rule: any module newly pulled into the api import graph must have its `@/` specifiers converted to relative `.js` ones, type-only imports included — a later edit can turn a type import into a value one.
- An allowlist is only safe when you derive it from the actual callers. Guessing the stage-transition action vocabulary produced an 11-value set for an app that writes 25, so every Kanban drag 422'd and silently reverted. The label was a bound parameter on a text column and `/api/db` already permitted writes to that table, so the allowlist bought no safety at all — validate types and presence, and only constrain a vocabulary when each value maps to a distinct code path.
- A column that does not exist fails a write with SQLSTATE 42703, and `NeonCompatibleClient` returns that as `{ error }` rather than throwing. `api/execute-action.ts` inserted an `audit_entries.source` column that was never in the schema, never checked the result, and reported success — zero rows had ever been written. Check the `{ error }` on every write whose success you are about to report to a user.
- Do not assert the state of external configuration that can be queried. I told the user CI would fail "until you add the NEON_DATABASE_URL secret" and gave them setup instructions; the secret had existed for a week, and `gh secret list --repo <owner>/<repo>` would have said so in one command. The same applies to `gh run list` for whether CI is actually red, `gh variable list`, and `gh api` for repo settings. Rule: before reporting that external state is missing or broken, query it — and if it genuinely cannot be queried, say "I cannot see whether…" rather than asserting it is absent.
- A gate that disarms itself when its input is missing is not a gate. Making `REQUIRE_LIVE` conditional on the secret being present would have let a removed or renamed secret turn CI green while testing nothing — the same "a check that did not run reported as clear" failure the codebase refuses everywhere else. Prefer a loud failure over a silent downgrade.
- A guard that tests whether a thing is *present* rather than whether it has the *property that matters* guards nothing. `assertFilteredWrite` required a filter on a destructive `/api/db` write and counted them — but `neq` with a null value and `is` with any value both compile to `col IS NOT NULL`, so one filter satisfied the guard and matched every row. Its own comment claimed it "removes the worst thing this endpoint can be made to do", which is what would have stopped the next reader from checking. Rule: when you write a guard, write its bypass test in the same commit — the input that satisfies the guard and still does the bad thing. If you cannot construct one, you do not yet know what the guard covers.
- A skip rule in the schema applier is a schema the file describes and no environment ever gets. `apply-neon-schema.mjs` silently discarded every `CREATE POLICY` and `ENABLE ROW LEVEL SECURITY` statement, so `db/schema.sql` described 47 RLS-enabled tables while the live database carried one — the same drift shape as the three `service_descriptions` columns, but caused by the tool rather than by an omission. Rule: a skip in the applier needs the same scrutiny as a missing migration; prefer deleting the statements over teaching the applier to ignore them, and have `test:schema-drift` assert the skip list stays empty.
- A test that writes to the live store must read the error from its own cleanup. `test:derived` deleted its fixtures with `.like('id', 'E2E-DRV-%')` and ignored the result; when a new write guard started refusing pattern matches the cleanup failed silently and the suite leaked a contract per run into production until an unrelated live check failed on the accumulation. Rule: cleanup is test code that can fail like any other — check its error, and delete by the exact ids the suite created rather than by a pattern it hopes only matches its own rows.
- Two copies of one helper diverge in the constants, not the signatures — which is exactly what types and tests do not catch. `src/lib/llm.ts` and `api/_llm.ts` both exported `callLLM` with an identical signature, option shape and defaults, and named **different Groq models**, so the assistant and four single-shot handlers had been running on different models with nothing saying so. Rule: when merging duplicates, diff the literals and the constants first; and when the difference turns out to be a product decision (a model id, a threshold, a timeout), make it an explicit parameter with each caller stating its choice rather than picking a winner.
- Do not write a data-access module from a remembered schema. Adding `src/lib/db/chat-feedback.ts` I gave it `user_id`, `conversation_id` and `comment` columns; the table has only `id`, `message_id`, `polarity`, `created_at`. Rule: read the `CREATE TABLE` block before writing the mapper — and if the real shape is thinner than expected, say so in the module rather than quietly working around it (feedback here cannot be attributed to a user or grouped by thread, which the analytics page will eventually want to know).
- Pin the property a test is about, not the whole call shape around it. The json-mode suite asserted `callGroq(groqKey, messages, temperature, maxTokens, jsonMode)` as an exact string, so adding a trailing `model` argument failed a test that has nothing to do with models. Rule: match the argument you care about with a boundary (`jsonMode[,)]`) rather than the full arity, so an unrelated signature change does not read as a regression.
- An instruction that cites a rule id must define it. `CLAUDE.md` said "Model selection is governed (CLS-G0)" and no file in the repository said what CLS-G0 required, so the rule could only be followed by people who already knew it. Rule: any policy id an instruction file leans on gets its terms written out at the point of citation — what is forbidden, what needs approval, and what to do when the thing it governs breaks on its own (here: Groq retires models on a rolling schedule and a retired id returns a 404 that reads like an outage).
- One run each way is not a bisect. Live suites here fail intermittently with `Error connecting to database: TimeoutError: The operation was aborted due to timeout` — three timed out in one sequential gate and none in the next, with the same working tree. I stashed my changes, saw `test:routing` pass in 1s, unstashed, and was about to report that I had broken it; re-running it twice with the changes present passed in 1s both times. The changes were React components that suite does not import, which should have been the first thing I checked rather than the last. Rule: before attributing an intermittent failure to a diff, (a) ask whether the diff is even in that suite's import graph, and (b) repeat each condition until the results separate — a single pass/fail pair across a flaky boundary is coincidence, and stashing makes it look like evidence.
- A guard against a control *appearing* must not match on how that control happens to be labelled. `test:reference-data-ui` asserted no delete on `/admin/cost-centres` with `getByRole('button', { name: /delete/i }).count() === 0`, and my icon-only trash button — which is how every other table in this product renders delete — sailed straight past it while the forbidden control was on screen and working. The guard passed and the decision it protected was already reversed. Rule: assert against the rendered markup or a stable attribute, not the accessible name, whenever the thing you are forbidding has more than one spelling; and verify a new "absence" guard by adding the thing back in the same commit.
- A colour token that flips between themes cannot have a fixed text colour pinned against it. Mapping status classes onto tokens produced `bg-ok text-white`: correct at 6.12:1 in light, and 2.32:1 in dark, where `--ok` inverts from a dark green to a light tint. All four status fills did this. Rule: text on a themed fill uses a token that flips with it (`--paper` here, which clears AA on every status in both themes) — and the contrast guard must check the *pairs a component actually renders*, not just each token against the page background. My hand check covered `--card` and `--paper` and missed `--card-2` and `--idle-soft`; the computed check found both in a second.
